The deferred-viewport approach shares one event loop, one context, and the state we already share.
- **Residual risk (the live gate of C7-21):** compositor-specific behavior of the spawned window (placement, decorations) must be verified on the host's Wayland session in the first integration chunk; if it fails, D-3b is the documented fallback and the plan is amended (a rebase-scale change, not silent).

## 4. DESIGN DECISIONS (each with a one-line rationale)

- **D-1 — Burn-in wire: a new `Request::StartBurnIn { target, duration_minutes }` arm, not an extended `StartBenchmark`.** A burn-in is a different run class (multi-pass duration run vs the single-pass `StartBenchmark`): extending `StartBenchmark` with a `duration_minutes` field would (a) change the frozen arm's shape for a case its existing consumers never use, (b) conflate "one pass" with "N minutes" in one request, and (c) leave `BenchMode` semantically dangling; a new arm reuses `StreamTarget`, keeps `StartBenchmark`/`BenchMode` byte-frozen, and rides the existing single-flight slot + `CancelBenchmark { run_id }` for stopping (brief: "stop via existing Cancel").
- **D-2 — Burn-in progress: a new `Response::BurnInProgress(BurnInTick)` arm, not an extended `StreamProgress`.** `StreamProgress.op` is a `BenchOp` (Read/Write/Copy — no latency arm) and carries no iteration/elapsed, so burn-in's per-iteration bandwidth **and** per-tier latency plus iteration/elapsed cannot ride it without polluting the normal-bench contract (every existing consumer — CLI, TUI, GUI live grid — parses `StreamProgress`); `BurnInTick` carries `iteration` + `elapsed_secs` + exactly one of `(op, gbps)` / `latency_ns`, is a new wire type owned by the bench crate (the `StreamProgress` ownership precedent), and leaves `StreamProgress`/`BenchProgress` byte-identical.
- **D-3 — Graphs window: eframe 0.27.2 native multi-viewport (`show_viewport_deferred` + per-frame re-registration + child-callback close handling), one deferred child OS window sharing `Arc<RwLock<TelemetryData>>`; NOT a second `eframe::run` on a dedicated thread.** The 0.27.2 API is stable and dependency-free (§1 spike: `show_viewport_deferred` context.rs L3154, the glow runtime's real-window creation + GC, `ViewportInfo::close_requested`, `IdTypeMap` view state — all verified in the vendored sources); the dedicated-thread alternative is the failure mode on the operator's **Wayland** host (winit event loop + `wl_display` thread affinity — a second loop on a non-main thread), and it duplicates the eframe lifecycle/context/style for no gain. The child window is a pure *reader* of the shared state (the poller stays the only writer, D6) and repaints on its own 16 ms cadence. **Live gate:** C7-21 verifies the spawned window on the host's compositor; D-3b (the dedicated thread) is the documented fallback if — and only if — that gate fails, via a plan amendment + rebase.
- **D-4 — Missing graph series: every series slot always renders; a source-less series (VDDCR_CPU — no source anywhere; CPU temp when no AMD thermal zone) renders a label-only row with an explicit `N/A (no source)` note and no fake geometry; it self-populates if a source appears, no layout change.** Omitting rows would reflow the window per host and hide that the metric is tracked; a flat 0 line would be a lie (0 ≠ N/A) — the label-only no-source row is the honest middle (the no-panic/honest-Na contract, D5).
- **D-5 — Live memory bandwidth series: a step series from the existing `latest_memory_read_bw` source (newest streamed/burn-in `Memory · Read` event, else the terminal grid's Memory-Read cell, else no samples yet) — NOT a continuous sampler.** A continuous background bandwidth run monopolizes every pinned core (the single-flight contract: "a bandwidth run monopolizes every pinned core") — unacceptable as an ambient poller behavior; the step series is free (it rides the existing bench/burn-in data), honest (flat between runs = the last measured value), and updates live during a burn-in (the per-iteration ticks feed it).
- **D-6 — AGESA: relax the `is_agesa_version` group2 bound to 1–6 digits; keep the DMI-bios scan primary and the existing `ryzen_smu` `version`-attribute fallback (both pass the relaxed shape); reject accepting the attribute verbatim without the shape check.** The host's only AGESA-shaped string is the smu `version` attribute `56.78.0` (group2 `"0"` = 1 digit, rejected today); the one-bound relaxation makes the existing fallback chain resolve it with the DMI scan still primary, while the shape guarantee (dotted-numeric, no prose) keeps arbitrary driver strings from masquerading as AGESA. Host result: `AGESA 56.78.0` in the header line 2.
- **D-7 — GDM/CR label format: one row, label `GDM / CR`, display `GEAR_DOWN: <Enabled|Disabled> · CR: <1T|2T>` — exact strings `GEAR_DOWN: Enabled · CR: 1T`, `GEAR_DOWN: Enabled · CR: 2T`, `GEAR_DOWN: Disabled · CR: 1T`, `GEAR_DOWN: Disabled · CR: 2T`; a not-applicable/failed cell degrades its own token to `N/A (<reason>)` and the combined cell is CRIMSON when either token is absent (the existing `cell_color` rule, re-pointed at the new strings).** The "Gear 1" wording is dropped (it collides with Intel gear-mode semantics — the brief's explicit concern); each token now carries its own name, so the row reads unambiguously on AMD, Intel-degraded, and Na combinations alike.
- **D-8 — Baseline-once mechanism: in `spawn_poller`, a thread-local `baseline_for: Option<String>` — exactly one `poll_telemetry` per *distinct* `settings.socket` value, regardless of `refresh_enabled`, stamping `last_poll` after each; continuous polling then requires `refresh_enabled && due` (the existing gate, unchanged); `refresh_enabled` defaults `false` (C7-09).** One startup baseline (the brief's item 1) without retry storms (a failed baseline = the normal friendly `disconnected` state; the next user action re-triggers); a socket edit re-triggers exactly one fetch so the settings panel is never a dead end with refresh off; enabling refresh resumes the full cadence one interval after the last fetch; the existing reconnect prime (series clear on disconnected→connected) is untouched and still applies.
