**Task 1 — AGESA: no real AGESA string is obtainable unprivileged (evidence, this host)**
- `strings /sys/firmware/dmi/tables/DMI | grep -iE "AGESA|Combo|PI [0-9]"` → **no lines**: the raw DMI table exists (3153 B) but is mode `0400 root:root` — `head`/`strings` as `madgoat` → `Permission denied`. The table's SMBIOS Type 11 (`BIOS Characteristic Extensions`, where AMD boards carry the real `ComboAm4v… PI x.y.z.n`) is unreadable without root.
- `dmidecode -t 11` (dmidecode 3.7 installed) → fails unprivileged: `/sys/firmware/dmi/tables/smbios_entry_point: Permission denied` (also `0400 root:root`) + `Can't read memory from /dev/mem`. No Type 11, no root.
- The unprivileged DMI sysfs (`/sys/class/dmi/id/`) exposes only the pre-parsed strings: `bios_version` = **`5601`** (a bare OEM build code — zero dots, rejected by `is_agesa_version`, no `AGESA` keyword, no `Combo` string).
- The only AGESA-shaped string on this host is `/sys/kernel/ryzen_smu_drv/version` = **`56.78.0`** — the **SMU firmware** version the `ryzen_smu` driver publishes, not an AMD AGESA release (the real AGESA string, e.g. `ComboAm4v2 PI 1.2.0.12`, lives only in the root-gated raw table/Type 11).
- Current chain: `platform.rs` `read_agesa()` (L168–172) → `agesa_from_sources(bios, smu)` (L251–259): DMI `bios_version` scan first, `ryzen_smu` version fallback; both pass the conservative shape check `parse_agesa`/`is_agesa_version` (L278–316, Cycle 7 D-6 relaxed group2 to 1–6 digits — that relaxation is what lets `56.78.0` through today). So the header's `AGESA 56.78.0` is the SMU firmware version mislabeled (the operator's report).
- **Consequence (D-1):** the real AGESA string is root-gated → the tool (unprivileged by design) must **relabel**: `agesa` = true AGESA only (the BIOS-string scan), and the SMU firmware version rides a new, separately-labeled `smu_version` field; the header shows `AGESA <v>` / `SMU <v>` / `AGESA N/A` by provenance — never `AGESA 56.78.0`.

**Task 2 — SPD: the live host's module bytes (read straight from the bound `ee1004` devices, both DIMMs identical: `5-0052`/`5-0053`)**
- The two G.Skill `F4-3600C18-32GVK` modules (a 2×16 GiB kit) expose, per 512-byte raw image: `0x00 = 0x23`, `0x01 = 0x11`, **`0x02 = 0x0C`**, `0x03 = 0x02`, `0x0C = 0x09`, `0x0D = 0x03`, **`0x13 = 0x0D`** (16 Gb density), `0x20 = 0x20` (3200 MT/s), **`0x80 = 0x11`**, **`0x81 = 0x11`**, `0x82 = 0x41`, `0x83 = 0x01`, part `F4-3600C18-32GVK` at `0x149`, serial blank at `0x91`, `0x62..0x65` all zero.
- **The code's classification is wrong for DDR4 (a latent bug this cycle fixes):** `classify_ddr5`/`is_ddr4` read the memory type from **byte `0x00` bits 4:0** (const `MEM_TYPE_DDR4 = 0x0A`, `MEM_TYPE_DDR5 = 0x0C`). Per the JESD79-4/JESD79-5 basic-info layout (JEDEC-sourced SPD reference, fetched + verified this recon): the basic memory type is **byte `0x02`** (`12 = DDR4`, i.e. `0x0C`; DDR5's `0x02` is its key byte, also `0x0C`, distinguished by the 1024-B image; DDR3 `0x02 = 0x0B`); byte `0x00` is `SPD bytes used` and byte `0x01` is `SPD revision` (typically `0x10..0x12`). Live: `0x00 = 0x23` (junk) but `0x02 = 0x0C` + 512 B → **DDR4**; the current code sees `0x23 & 0x1F = 3` → "not DDR4" → `decode_part` falls to the legacy `0x81` location → the first byte `0x11` is non-ASCII → **part = `Na(NotApplicable)` on the live host** (the Cycle 7 deferred live check "SPD part on live host" fails for this root cause, not for the offset).
- **JESD79-4 module-organization bytes (the decode fix, D-2):** byte `0x0C` = rank mix (bit 4) / **package ranks per DIMM − 1 (bit 3)** / **SDRAM device width (bits 2:0)**; byte `0x0D` = bus-width extension (bit 4) / primary bus width (bits 3:0); the module-specific section `0x80..0x83` is family-dependent (the current code models `0x80` as `upper = total devices, lower = per-rank` and reads **only** `0x80`). Live decodes to: `0x0C = 0x09` → **1 rank, x8 width**; `0x80 = 0x11` → per-rank nibble **1** (the vendor's hub bytes are non-compliant: `1 × 8 bits ≠ 64-bit bus`, and the `0x82 = 0x41`/`0x83 = 0x01` fields are undefined in this model — G.Skill hand-wrote this hub area, same family as the `0x00 = 0x23` junk). The module is a 1R x8 UDIMM of 16 Gb dies → physically **8 devices per rank → 16 GiB** (the part's kit math agrees: 32 G kit ÷ 2 = 16 GiB). The current decode (`devices = 0x80 lower = 1`) → `16384 Mbit × 1 / 8192 = 2 GiB` → the header's `2x2 GiB` / `4 GiB` (the operator's report).
- **Width-encoding corroboration:** `0x0C bits 2:0 = 1` = x8 (the `0 = x4 / 1 = x8 / 2 = x16` code — the JESD79-5 `0x81` width convention, which the live `0x81 = 0x11` lower nibble = 1 agrees with). x8 is the only width consistent with 1 rank + 16 GiB + 16 Gb dies (a 1R x4 UDIMM cannot exceed 8 dies = 4 GiB; a 1R x16 would be 4 dies = 8 GiB) → the code is validated by the live module's own physics.
- **`facade.rs`:** `dimm_sizes()` (L241–252) = `density_mbit × devices / 8192` — consumes `SpdModule.devices` as the **total** count, but the decode supplies the **per-rank** nibble (the bug, D-2); `total_capacity()` (L260–274) = SPD sum when any cell is a `Value`, **else** `platform::mem_total_gib()` — bogus `Value` cells (2 GiB each) block the fallback, so the OS truth (`MemTotal` = 65728012 kB = **62.68 GiB** ≈ the host's 64 GB minus reserved) is discarded (D-3). Only the 2 SPD-bound DIMMs are visible; the remaining ~32 GiB sits in slots whose EEPROMs are not bound to `ee1004` → the SPD sum can never equal the OS total on this host → **the total must prefer `MemTotal`** (D-3); per-slot sizes stay SPD-derived (D-2's corrected decode → 16 GiB each → `2x16 GiB`).
- GUI: `main.rs` `ram_line_prefix` (L597–608: `format_capacity(total)` + `dimm_summary(&t.dimm_sizes)`), `dimm_summary` (L557–576: groups equal sizes → `2x16 GiB`), `format_capacity` (settings.rs L167–175: `trim(gib)` + ` GiB` — `62.68` stays `62.68 GiB`). ## 4. DESIGN DECISIONS (each with its ruling + evidence)

- **D-1 — AGESA: honest relabel, not a fabricated string.** The real AGESA string (`ComboAm4v… PI x.y.z.n`, SMBIOS Type 11 / raw DMI table) is **unobtainable unprivileged**: the raw table `/sys/firmware/dmi/tables/DMI` (3153 B) is `0400 root:root` (`strings`/`head` as the operator user → `Permission denied`), `dmidecode -t 11` fails on the `0400` entry point + unreadable `/dev/mem`, and the unprivileged DMI sysfs `bios_version = "5601"` carries no AGESA token. The only AGESA-shaped string on the host is the `ryzen_smu` `version` attribute `56.78.0` — the **SMU firmware** version, not AGESA. Ruling: (a) `agesa` narrows to the true-AGESA scan (DMI BIOS string only — a host whose BIOS string carries `AGESA 1.2.0.12` still resolves it; shape-checked as today); (b) the SMU version moves to a new additive `smu_version` field (shape-checked, never verbatim — the C7 D-6 guarantee stands); (c) the header fragment shows `AGESA <v>` when `agesa` is a `Value`, else `SMU <v>` when `smu_version` is a `Value`, else `AGESA N/A` — the operator host reads `… (BIOS: 5601, SMU 56.78.0)`. No `AGESA/SMU` hybrid (one value, one true label) and no SMU value folded under the `AGESA` label (the reported defect). The tool stays unprivileged by design — a root-mode AGESA read is a follow-up, not this cycle.
- **D-2 — Per-slot capacity: `devices` = TOTAL device count, generation-scoped JESD79-4/5 decode with a bus-width consistency rule.** (a) **Classification first (the latent fix):** the memory type is byte `0x02` (`0x0C` = DDR4 on a 512-B image; `0x0C` + 1024-B = DDR5 key byte; `0x0B` = DDR3 legacy) — the old byte-`0x00` read misclassifies the live host (`0x23`) and silently breaks its part decode (`0x149` → legacy `0x81` → `Na`); the byte-`0x00` check is kept as a documented legacy fallback (older synthetic/quirky images + the existing test fixtures), then the image-length fallback (the current behavior). (b) **Total devices:** DDR4 — rank = `0x0C` bit 3 + 1 (the JEDEC "package ranks per DIMM − 1"; the live `0x09` → 1), width = `0x0C` bits 2:0 (`0 = x4 / 1 = x8 / 2 = x16`; fallback `0x81` bits 2:0, same code — the live `0x81 = 0x11` lower = 1 = x8 agrees), per-rank = `0x80` bits 3:0 **when** `per_rank × width_bits == bus_bits` (the 64-bit desktop bus + the `0x0D` bit-4 extension), **else derived** as `bus_bits / width_bits`; total = rank × per-rank. Live: `1 × 8 = 8 ≠ 64` → derived `64 / 8 = 8` → total **8** → `16384 Mbit × 8 / 8192 = 16 GiB` (the vendor's non-compliant hub — `0x80 = 0x11`, `0x82 = 0x41`, `0x83 = 0x01` — is worked around, never trusted when it fails the bus check). DDR5 — the hub model (rank = `0x80` bits 7:4, per-rank = `0x80` bits 3:0, width = `0x81` bits 2:0, `0/1/2 → 4/8/16`) with the same consistency/derivation (documented model — the live host is DDR4; the `ddr5_image` fixture is re-anchored to it). (c) `SpdModule.devices` carries the **total** (semantic fix; `dimm_sizes` = `density × devices / 8192` needs no code change); invalid gating: per-rank `0`, unknown width, or a non-dividing bus → `Na(ParseError)` (the reason names the byte). The live-shape test pins: `0x13 = 0x0D` + `0x80 = 0x11` (+ the corroborating `0x0C = 0x09`, `0x81 = 0x11`, `0x02 = 0x0C`) → rank 1, per-rank 8 (derived), total 8, **16 GiB**.
- **D-3 — Total capacity: `MemTotal` preferred, SPD sum demoted to the non-meminfo fallback.** The SPD enumeration is structurally incomplete on this host (2 `ee1004`-bound DIMMs, `MemTotal` = 65728012 kB = 62.68 GiB — the other ~32 GiB sits in slots with no bound EEPROM), so a *sum* of what SPD sees can never equal the OS total, and today's "sum when any cell is a `Value`" rule lets bogus `Value` cells (2 GiB each) block the meminfo fallback — the reported `RAM: 4 GiB`. Ruling: `total_capacity = MemTotal` (when it is a `Value` — the OS is the ground truth for installed memory; it reads slightly under the marketing figure because of reserved memory, which is the honest OS view) **else** the SPD sum (non-Linux / meminfo-absent hosts) **else** `Na`. The SPD sum survives as a pure helper (`sum_dimm_sizes`, unit-tested: `8 + 16 = 24`, single value = itself, all-`Na` = `Na`). Per-slot sizes stay SPD-derived (D-2) → the RAM line reads `RAM: 62.68 GiB (2x16 GiB) 3200 MT/s | Dual-Channel | …`. No per-slot "scaling" to the OS total (that would fabricate a 4-DIMM config the unprivileged surface cannot verify — 2×32 GiB is equally consistent with 62.68 GiB; the per-slot truth is the SPD's own corrected decode).
- **D-4 — N/A formatting: bare `N/A`, GUI-scoped.** Every GUI `na_text` arm (zone 1 + zone 3) and the hardcoded placeholders (`N/A (no telemetry)` ×2, `SPD: N/A (driver missing)`, `N/A (no source)`) render **bare `N/A`** — the reason stays on the wire (`NaReason`) for the CLI/TUI and the no-panic contract, the GUI drops the parenthetical as verbose. **Scope ruling:** the out-of-GUI twins (`ramsleuth-tui` `na_text`/`na_item`/`section_na`, `ramsleuth-client` `na_cell`/`section_state`) keep their verbose forms this cycle — the operator task is GUI-focused and the CLI's column-aligned dump benefits from the reason text; the consistent TUI/CLI restyle is a documented follow-up (§8).

**Sliding window 2:** while the implementer works `branch/chunk-c8-NN` (worktree `../ramsleuth-wt-c8-NN`), the reviewer works the just-completed `branch/chunk-c8-(N-1)` — runs that chunk's verification gate, lease-signs it in `DEV_LOG.md`, `git merge --no-ff`s into `v2-development`, and prunes the branch + worktree. The implementer commits `feat(c8-NN): …` and pushes the branch to origin (local-only; the operator-gated push of `v2-development` itself stays O6 — **no push of the base branch this cycle, never force-push**).

**Rebase trigger:** after every merge to `v2-development`, the in-flight branch rebases onto the new tip before its review (the house rule — a branch that forked before a landed change cannot review against stale code). C8-01 co-lands ~20 test literals across 13 files in one commit, so any in-flight branch touching one of those files rebases onto the freeze (by the order above the only in-flight candidate when C8-01 lands is C8-02 — different file, no conflict expected; the literal ripples are one-line additions). If a rebase reveals a conflict in a FROZEN SHAPE (§3 — the `smu_version` field, the `devices`-total semantics, the `NA_GRAY` const), stop — it is a plan edit, not a merge.

**Circuit-breaker rule (hard stop, the C7 refinement carried over):** the pipeline halts and the reviewer returns `STATUS: FAILED` on any of: (a) a **production (non-test) compile failure in any crate at a gate boundary** — `cargo check --workspace` (non-test targets) not clean after a merge (the hard invariant — C8-01's co-landing exists precisely to keep it); (b) `cargo clippy --workspace --all-targets -- -D warnings` non-clean; (c) **any baseline test red at a gate boundary** (the 515 baseline + the cycle's additions, debug or release); (d) a **no-panic / no-segfault** violation (a panic, a crash in any privilege × CPU state, a sentinel decoded as data — the SPD decode is bounds-checked pure, the new `0x0C`/`0x0D`/`0x81` reads go through the existing `get` helper); (e) a FROZEN-SHAPE change beyond §3 without a plan edit (e.g. a second wire field, a `SpdModule` shape change, deleting `AGESA` rather than re-scoping it). On a trip: exact diagnostics to `DEV_LOG.md`, the offending branch is not merged, the pipeline resumes only after the defect is fixed and its gate re-run.

**No gates / no parking:** nothing here is hardware-gated — every item runs on the 5950X host today (the host's quirks — the non-compliant G.Skill SPD hub, the root-gated DMI table — are the *inputs* the decode is pinned against, §1). The operator's only role is the final live run (§7).
